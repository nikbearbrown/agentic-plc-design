## Executive summary

Edit a drawing by script, safely, with no CAD program: fill a title block, swap a pump rating everywhere it appears, renumber wire labels, and pull a device list out of the drawing to cross-check it against the design. The tool is [ezdxf](https://ezdxf.readthedocs.io/), an open-source (MIT) Python library that reads and writes DXF files, so an AI agent can run the whole lab itself and prove what it changed. It is the agent-runnable twin of Module 4, which uses AutoLISP inside DraftSight and has never been run by the course author.

The safety pattern is the same in both: **plan by default, write only to a new copy, verify afterwards, keep an audit log.** This lab adds the part AutoLISP could not give us: after writing, the tool reloads the file and *proves* that only the planned text changed.

**What this lab does not establish.** It does not show that DraftSight, AutoCAD or any CAD program opens the edited file correctly, that DWG files behave the same (ezdxf reads DXF only), or that real shop drawings (with external references, proxy objects, or heavily formatted text) edit cleanly. The drawing is synthetic. A person with the real CAD program must try the output.

## 1. Look before you edit

The fixture is `labs/dxf/station-a.dxf`: a synthetic sheet with a title block, a device schedule, notes, a revision-history line, and wire labels. It was generated by `scripts/make_sample_dxf.py`; no customer material is involved.

Pull the device list out of the drawing and cross-check it against the design:

```sh
python3 project/tools/apd.py dxf extract labs/dxf/station-a.dxf > scratch/drawing-extract.csv
python3 project/tools/apd.py crosscheck project/variants/a-baseline.toml scratch/drawing-extract.csv
```

**Prediction first.** Before running the second command, open `scratch/drawing-extract.csv` and the design's device list (`python3 project/tools/apd.py devices project/variants/a-baseline.toml`) side by side. Write down every disagreement you can find.

Expected output: three findings, the same three as the CSV exercise in Module 3: `P2_OL1` missing on the drawing, `P3_K1` not in the design, and a rating mismatch on `P1_K1`. This time the CSV came from the drawing file itself, not from a hand-built sample.

## 2. Plan a rating swap (nothing is written)

```sh
python3 project/tools/apd.py dxf replace labs/dxf/station-a.dxf "7.5 HP" "10 HP"
```

Each line shows the entity type, layer, handle, old text and new text. The last line says `planned; nothing written`. Check that the original file's hash is unchanged if you like: `shasum labs/dxf/station-a.dxf` before and after.

**Prediction.** The drawing contains the string `7.5` in several places. Which will this plan change, and which should it change? Decide before reading the answer.

<details>
<summary>Answer key (read after predicting)</summary>

The plan changes five strings: two device descriptions, the pump note, an MTEXT motor note, and a revision-history line. It correctly leaves `CABLE LENGTH 7.5 FT` alone because the pattern is `7.5 HP`, not `7.5`. The judgment call is the **revision-history line** on layer `REV-HISTORY`: that text records what the original issue *was*. Rewriting it to say `10 HP` falsifies the history. Add `--exclude-layer REV-HISTORY` and the plan drops to four changes. Whether history is excluded is a decision for the drawing's owner, not the tool.
</details>

Run it again with the exclusion and compare:

```sh
python3 project/tools/apd.py dxf replace labs/dxf/station-a.dxf "7.5 HP" "10 HP" --exclude-layer REV-HISTORY
```

## 3. Apply to a copy, and see it refuse

```sh
python3 project/tools/apd.py dxf replace labs/dxf/station-a.dxf "7.5 HP" "10 HP" --exclude-layer REV-HISTORY --apply --out scratch/station-a-10hp.dxf
```

Expected: `4 change(s) applied`, an audit log path, and `verified: reloaded output; only the planned text differs`. The file `scratch/station-a-10hp.dxf.changes.json` lists every old and new value with its handle.

Now try the unsafe things. Both must be refused, and the second must leave the first output untouched:

```sh
python3 project/tools/apd.py dxf replace labs/dxf/station-a.dxf "7.5 HP" "10 HP" --apply --out labs/dxf/station-a.dxf
python3 project/tools/apd.py dxf replace labs/dxf/station-a.dxf "7.5 HP" "10 HP" --apply --out scratch/station-a-10hp.dxf
```

Expected: `refused: --out is the input file`, then `refused: ... already exists`.

## 4. Title block and wire numbers

```sh
python3 project/tools/apd.py dxf title labs/dxf/station-a.dxf --variant project/variants/a-baseline.toml
python3 project/tools/apd.py dxf renumber labs/dxf/station-a.dxf --layer WIRES --prefix W --start 1
```

The title-block fields come from the same variant file as the I/O list and BOM, so the drawing cannot drift from them. If a block is not found, the tool says so instead of silently doing nothing; try `--block NO_SUCH_BLOCK` on the first command.

**Prediction.** The wire labels are `W014 W003 W009 W001 WIRE NOTE W020`. What will the plan say? Check it against: order is top-to-bottom then left-to-right by position, and a label that is not a wire number is skipped. Note that a renumber can turn one existing label into another that already exists (`W001` is both an old and a new name here). Why is that dangerous on a real drawing, and what would you check?

## 5. Let the agent do it, and check the agent

Give your agent this work order:

> Work on the DXF lab only. Use `python3 project/tools/apd.py dxf`. Never write to `labs/dxf/station-a.dxf`; output goes under `scratch/`. First show me the plan for changing `7.5 HP` to `10 HP` with the `REV-HISTORY` layer excluded and wait. After I approve, apply it to `scratch/station-a-10hp.dxf`, open the `.changes.json` log, and tell me (a) how many changes, (b) the SHA-256 of the original before and after, and (c) whether the tool's own verification line appeared. Then extract a device list from the new file and run the cross-check. State which of these results you ran yourself and which you only read.

Check the agent against what you saw yourself: the count, the hashes, the verification line, the three cross-check findings. A claim you cannot reproduce with one command is not evidence.

## 6. Compare with the AutoLISP route (needs DraftSight; this is the human part)

Module 4 does the same job in DraftSight with `apd-lib.lsp`. The point of doing both is to find out where they differ. A person with DraftSight should record, in `feedback/`, using the feedback template:

- Does the edited `.dxf` open in DraftSight? Do the title block fields and notes look right?
- Does the AutoLISP dry run list the same changes as this plan? (A difference is a finding about one of the two tools.)
- Does DraftSight's own attribute extraction give the same device list as `dxf extract`?

## Assessment

Submit (1) the plan and applied-run outputs, (2) the `.changes.json`, (3) your decision on the revision-history line with a one-sentence reason, (4) one case where the tool's verification could still pass while the drawing is wrong, for example a rating written in a symbol, a block definition, or a drawing outside the layers the tool reads. The tool reads TEXT, MTEXT, and block attributes in model space and paper space; it **never** edits block definitions.
